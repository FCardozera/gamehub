# ADR-0002: BIGINT IDENTITY primary keys over UUID

## Status

Accepted

## Context

Every entity in GameHub needs a primary key. The two realistic options are a
database-generated sequential integer (`BIGINT GENERATED ALWAYS AS IDENTITY`)
and a UUID.

The choice affects three things: index performance, storage size, and whether
identifiers are guessable from the outside.

**UUID** identifiers are not sequential and not guessable, which prevents an
enumeration attack: with sequential integers, a request to `/players/5`
reveals that players 4 and 6 probably exist, allowing an attacker to map the
whole dataset. UUIDs can also be generated by the application without a
round trip to the database.

However, a random UUID (v4) is a poor fit for a B-tree index. Indexes perform
best with sequential inserts; random values scatter writes across index pages,
causing fragmentation and extra I/O. A UUID also occupies 16 bytes against 8
for a BIGINT, and that cost is repeated in every secondary index that
references the key.

GameHub currently has no requirement that justifies UUIDs. The API is not yet
public, and no entity needs client-generated identifiers.

## Decision

Use `BIGINT GENERATED ALWAYS AS IDENTITY` as the primary key for all entities.

`GENERATED ALWAYS AS IDENTITY` is chosen over the legacy `BIGSERIAL` because
it is standard SQL, cleaner, and the `ALWAYS` clause prevents a manual insert
from breaking the sequence. `BIGINT` is chosen over `INT` because the extra
four bytes per row remove any risk of overflow, and migrating an integer key
to a larger type on a large production table is an expensive operation.

## Consequences

**Positive**

- Sequential inserts keep the primary-key index compact and efficient.
- Smaller keys mean smaller indexes and less I/O, including in every table
  that references a player.
- Simpler to read and debug during development than opaque UUIDs.

**Negative / trade-offs accepted**

- Identifiers are enumerable. Exposing a raw `BIGINT` in a public URL leaks
  information about the size and growth of the dataset.

**Mitigation, if the exposure becomes a real concern**

- Keep the internal `BIGINT id` for joins and relationships, and add a
  separate `public_id UUID` column that is the only identifier exposed
  through the API. This isolates the performance-sensitive internal key from
  the externally visible one.
- If a fully sequential and non-guessable key is ever needed, UUIDv7 (which
  embeds a timestamp prefix and is therefore index-friendly) resolves both
  concerns at once.

This decision is revisited if and when the API is exposed publicly with
sensitive per-entity endpoints.
